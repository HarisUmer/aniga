# Database

**Where:** `infra/docker-compose.yml`, `infra/db/init/`.
**Engine:** PostgreSQL 17 (Alpine image), host port **5433** (5432 is often taken by a local install).

## How it starts

The official Postgres image runs every `*.sql` file in `/docker-entrypoint-initdb.d` in alphabetical order, **only when the data volume is empty**:

1. `001_schema.sql` — tables and indexes
2. `002_seed.sql` — 33 titles, 3 demo users, ratings, the MangaDex adapter row
3. `003_source_catalog.sql` — generated by `tools/source-ingest/ingest_sources.py`

A healthcheck (`pg_isready`) gates the backend so it never starts against a half-initialised DB.

## Tables and why they exist

| Table | Purpose | Design notes |
|-------|---------|--------------|
| `app_user` | Users | Named to avoid Supabase's `auth.users` when we migrate |
| `media` | Anime, manga, manhwa, manhua in one table | `media_type` CHECK constraint; `genres`/`tags` as `text[]` with a GIN index for "contains genre" queries; `(external_source, external_id)` unique so AniList/MangaDex sync can upsert |
| `rating` | 1–10 score per user and title | Composite primary key = one rating per pair; upsert with `ON CONFLICT` |
| `library_entry` | Planning / current / completed / dropped + progress | Feeds "continue reading" and is a weak taste signal |
| `interaction_event` | Ordered log: impression, click, chapter read, episode watched, rate, skip, drop | Index on `(user_id, occurred_at)` because the LSTM reads a user's events in time order |
| `source_catalog` | Sites listed in public extension indexes | Metadata only; `content_hint` (MANGA/MANHWA/MANHUA/MIXED) and `nsfw` |
| `source_adapter` | Sources the app can actually read | `kind` = OFFICIAL_API or CMS_FAMILY |
| `chat_room`, `chat_member`, `chat_message` | Phase 7 chat | Membership table is what Supabase row-level security policies will check |

## Why arrays instead of join tables for genres/tags

- Read pattern is "give me the title with its genres", almost never "update one genre".
- One row = one document for the recommender; no N+1 joins.
- GIN index still supports `WHERE genres @> '{Action}'`.
- Trade-off: no foreign key on genre names. Acceptable while genres come from a fixed AniList vocabulary.

## Useful queries

```sql
-- Ratings with titles for a user
SELECT m.title, r.score FROM rating r JOIN media m ON m.id = r.media_id WHERE r.user_id = 1;

-- Manhwa-leaning English sources in the catalog
SELECT name, home_url FROM source_catalog WHERE content_hint = 'MANHWA' AND lang = 'en' AND NOT nsfw;

-- Titles containing a genre (uses the GIN index)
SELECT title FROM media WHERE genres @> '{Drama}';
```

Run them in Adminer (http://localhost:8081) or `docker exec -it aniga-postgres psql -U aniga -d aniga`.
